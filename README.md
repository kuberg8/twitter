# Fullstack app

## Использование в режиме разработки

### Настройки `.env`

Пример настроек см. файл `.env.example`

Для ведения разработки создайте файл `.env` копированием из файла `.env.example` и отредактируйте его в соответствии с потребностями в папках frontend и backend.

### Запуск проигрывателя в режиме "горячей" перезагрузки изменений

```bash
docker compose up -d --build
```

```npm script
npm run dev:up
```

Приложения будут доступны по адресам

- frontend - `http://localhost:3001`
- backend - `http://localhost:3000`
## Фоновые push-уведомления

Подписка включается кнопкой **«Включить push-уведомления»** в чате отдельно на каждом устройстве. Пользователь разрешает уведомления в системном диалоге. На iPhone/iPad (iOS 16.4+) сначала добавьте сайт на главный экран через «Поделиться» → «На экран Домой» и откройте его с иконки.

В общем чате backend отправляет уведомления всем подписанным пользователям, кроме автора. В личном чате уведомление отправляется только получателю. Изменение и удаление сообщений не вызывают push. Подписки хранятся в MongoDB, не зависят от открытой вкладки или WebSocket. Выход из аккаунта отключает уведомления на устройстве; обработчик также проверяет получателя, чтобы не показывать push от предыдущего аккаунта.

### Настройка ключей

```bash
npm ci --prefix backend
npm run push:setup --prefix backend -- https://twitter-front-v3y5.onrender.com
```

Команда добавляет `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` и `VAPID_SUBJECT` в локальный `backend/.env`, исключённый из Git. При повторном запуске существующая пара ключей сохраняется. Не генерируйте новую пару при каждом деплое: старые подписки связаны с исходным ключом.

### Публикация на Render

1. Опубликуйте изменения backend и frontend через существующий процесс деплоя.
2. В **backend-сервисе → Environment** добавьте три переменные из локального `backend/.env`: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`. Остальные существующие настройки оставьте на месте. Закрытый ключ не добавляйте во frontend и не коммитьте.
3. Пересоберите backend, чтобы установилась зависимость `web-push`, и frontend командой `npm run build`. Во frontend должны оставаться реальные HTTPS/WSS-адреса backend в `REACT_APP_API_URL` и `REACT_APP_WEBSOCKET_URL`, а не localhost.
4. Убедитесь, что `/push-sw.js` на frontend отдаётся как JavaScript, а не HTML fallback. Для Render Static Site можно добавить в Headers правило `/push-sw.js` → `Cache-Control: no-cache`. В приложенном Nginx конфиге оно уже есть.
5. Откройте обновлённый сайт, войдите и включите уведомления. На втором устройстве войдите **другим аккаунтом**, закройте чат на первом устройстве и отправьте сообщение со второго. Нажатие на уведомление должно открыть чат.

Если ключи не настроены, интерфейс прямо сообщает об этом. Истёкшие подписки (ответы провайдера 404/410) удаляются автоматически. Если ключи пришлось сменить, при следующем открытии чата старая подписка удаляется и уведомления нужно включить снова.

Звук системного push определяется настройками телефона; `sms.mp3` используется только открытой страницей. Доставка зависит от разрешений, сети и режима «Не беспокоить». Отправка выполняется после сохранения сообщения, без отдельной долговечной очереди: при перезапуске сервера во время отправки или временном сбое push-провайдера отдельное уведомление может быть потеряно, само сообщение остаётся в чате. На бесплатном Render после простоя backend может запускаться с задержкой.

Проверки:

```bash
npm test --prefix backend
CI=true npm test --prefix frontend -- --watchAll=false --runInBand --watchman=false
npm run build --prefix frontend
```

Документация: [Web Push для iOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [переменные Render](https://render.com/docs/configure-environment-variables), [ограничения бесплатного Render](https://render.com/docs/free).


## Личные чаты и мобильный режим

- Нажмите **«Новый чат»**, найдите участника по имени и выберите его. Диалог появится в списке после первого сообщения; существующие диалоги упорядочены по последнему сообщению.
- Общая лента остаётся отдельным чатом. Черновики сохраняются в памяти при переключении диалогов, но не после перезагрузки страницы.
- В модели Post поле `recipient` хранит получателя; `null` и отсутствие поля означают общий чат. Старые сообщения остаются общими, миграция не требуется.
- История личного диалога доступна только двум участникам. Проверка выполняется на сервере. Это разграничение доступа, не сквозное шифрование.
- API: `GET /chats`, `GET /chats/users?q=имя`, `GET /chats/users/:id`, `GET /posts?peer=<id>`, `POST /posts` с `{ "message": "Привет", "recipient": "<id>" }`. Все маршруты требуют Bearer-токен.
- WebSocket теперь требует сообщение `{ "type": "auth", "token": "..." }` и отдаёт события `posts:changed` только участникам. Событие содержит действие `created`/`updated`/`deleted` и одно сообщение с публичными полями автора. Создание/редактирование выполняется через REST. Обновляйте backend и frontend вместе; старые WebSocket-клиенты больше не поддерживаются.
- Push личного сообщения открывает конкретный диалог по `?chat=<id>`.
- Убраны жесты масштабирования страницы, Ctrl/Cmd+колесо и клавиатурный зум. Обычная прокрутка и ввод остаются доступны; поля ввода имеют размер шрифта не меньше 16px. Настройки доступности ОС и принудительный зум через меню браузера сайт контролировать не может.

Проверка после публикации: войдите тремя аккаунтами. Отправьте личное сообщение от A к B, убедитесь, что оно доступно A и B, но отсутствует в общем чате, списке диалогов и уведомлениях C. Закройте чат B, отправьте ещё одно сообщение и проверьте переход в диалог из push. На телефоне проверьте жесты масштабирования и обычную прокрутку.


## Интерфейс, темы и скорость

- Интерфейс мессенджера: диалоги слева, хронологическая история с разделителями дат, свои сообщения справа, поле ввода снизу. На телефоне — отдельные экраны списка и переписки, кнопка возврата в шапке. При чтении старых сообщений лента не прыгает вниз; к последним можно перейти отдельной кнопкой.
- В настройках (шестерёнка) доступны **«Как в системе»**, **«Светлая»** и **«Тёмная»**. Предпочтение хранится в `localStorage`, применяется также к входу/регистрации и синхронизируется между вкладками. Системный режим реагирует на изменения ОС без перезагрузки.
- В памяти сессии кешируются история (30 секунд до повторной проверки при открытии), список диалогов (30 секунд), профили (5 минут) и результаты поиска (1 минута). Повторные запросы объединяются; устаревшие данные остаются видимыми во время обновления. До 40 неактивных/активных записей в кеше с вытеснением неиспользуемых; активные и выполняющиеся запросы временно могут превышать лимит. Переписка не записывается в localStorage. Выход из аккаунта очищает кеш.
- Одно WebSocket-соединение на сессию, без переподключений при выборе чата. Новые сообщения, правки и удаления обновляют кеш напрямую. HTTP-проверка каждые 30 секунд нужна только при потере WebSocket и только в видимой вкладке. После восстановления связи/возврата во вкладку выполняется синхронизация.
- `GET /posts?peer=<id>&before=<cursor>` теперь возвращает `{ posts, nextCursor }`: последние 50 сообщений в хронологическом порядке. `nextCursor` используется кнопкой **«Более ранние сообщения»**. Курсор содержит дату и ID для стабильной пагинации; сервер ограничивает выдачу и использует `lean()` и составные индексы.
- HTTP-ответы с приватной перепиской имеют `Cache-Control: private, no-store`, чтобы их не кешировал общий CDN. Кеш приложения остаётся изолированным для текущего пользователя.
- Backend и frontend нужно публиковать вместе из-за нового формата истории и WebSocket-событий. Индексы описаны в модели Post; если в production отключён `autoIndex`, создайте их отдельно перед проверкой скорости на большой базе.

Эти изменения уменьшают число запросов и размер выдачи; время ответа на реальном Render не замерялось. Кеш приложения не устраняет холодный запуск бесплатного backend после простоя.
